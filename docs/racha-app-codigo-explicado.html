0.1 Como usar este material

Cada arquivo da pasta lib/ tem uma seção aqui, na ordem em que faz sentido aprender: primeiro a base (modelos, banco), depois a lógica, por último as telas, que usam tudo o que veio antes.

Nada é explicado duas vezes. Quando um arquivo repete algo que já apareceu em outro, a seção mostra uma caixa cinza assim:

Já explicado em 8.1 login_screen.dart: Form, TextFormField, validator e o botão com carregamento.

e só explica o que aquele arquivo tem de novo. Então, se a pergunta do professor cair num trecho que parece "pulado", siga o link da caixa cinza — a explicação está lá.

O código mostrado aqui são os trechos que importam, não o arquivo inteiro. Os comentários do próprio código (em cinza itálico) também valem como explicação — no projeto eles explicam o porquê de cada decisão.

Dica de estudo: leia a Parte 0 inteira primeiro. Ela explica os conceitos que aparecem em praticamente todo arquivo (ref.watch, async/await, AsyncValue…), e o resto do material parte do princípio de que você já sabe o que eles são.

0.2 O mapa do app

O código é dividido em camadas. Cada uma tem uma responsabilidade e só conversa com a camada vizinha:

PastaO que fazConhece o Firebase?
screens/As telas. Mostram dados e chamam ações.Não (no máximo o tipo GeoPoint)
widgets/, core/widgets/Pedaços de tela reaproveitados (avatar, seletor de foto).Não
providers/Liga tudo: entrega dados para as telas e executa as ações (os "controllers").Só para criar as instâncias
repositories/Lê e grava no Firestore. Uma classe por coleção.Sim
services/Fala com o mundo de fora: login, GPS, busca de endereço, notificação.Sim
models/As "fichas" de cada coisa: usuário, racha, grupo, participante…Só tipos (Timestamp, GeoPoint)
core/Lógica pura: balancear times, calcular ranking e MVP, tema, rotas.Não (no máximo o tipo GeoPoint)

O caminho de qualquer ação do app é sempre o mesmo. Exemplo: o jogador aperta "Confirmar presença":

Tela→ Controller→ Repository→ Firestore→ Stream avisa→ Tela se redesenha

A tela não atualiza a si mesma depois de gravar. Ela está "ouvindo" o banco (um stream), e quando o dado muda lá, ela se redesenha sozinha. Isso é o que faz o app mostrar a mudança no celular de todo mundo ao mesmo tempo.

Por que separar assim? Porque a lógica importante (balancear times, calcular ranking) fica em core/, sem nada de Firebase, e por isso dá para testar com flutter test sem internet e sem banco. São 62 testes, todos dessa parte.

0.3 Conceitos que aparecem em todo lugar

Estes conceitos aparecem em quase todos os arquivos. Quando um arquivo usar um deles, ele aponta para cá (C1, C2…).

C1Widget, StatelessWidget e StatefulWidget

No Flutter, tudo que aparece na tela é um widget: texto, botão, coluna, a tela inteira. Todo widget tem um método build, que devolve o que desenhar.

  • StatelessWidget — não guarda nada que mude. Recebe dados e desenha.
  • StatefulWidget — tem uma classe State separada que guarda valores que mudam (o que foi digitado, se está carregando). Para mudar um valor e redesenhar, chama setState(() { ... }).
class _CriarRachaScreenState extends ConsumerState<CriarRachaScreen> {
  DateTime? _data;                         // valor que muda

  Future<void> _escolherData() async {
    final data = await showDatePicker(...);
    if (data != null) setState(() => _data = data);   // muda e redesenha
  }
}

O _ no começo do nome (_data, _CriarRachaScreenState) significa privado: só esse arquivo enxerga.

C2const, final, late e parâmetros nomeados

  • final — recebe valor uma vez e nunca mais muda.
  • const — o valor é conhecido já na compilação. Num widget, const Text('Olá') deixa o Flutter reaproveitar o mesmo objeto em vez de criar outro a cada redesenho.
  • late — "vou dar valor depois, antes de usar". Usado quando o valor depende de algo que só existe no initState.
  • {required this.nome} — parâmetro nomeado: quem chama escreve UserModel(nome: 'Ana'). required obriga a passar.
  • super.key — repassa a key para a classe mãe. A key ajuda o Flutter a reconhecer o mesmo widget entre redesenhos. Todo widget tem por padrão.

C3Null safety: ?, !, ?? e ?.

  • String? — pode ser nulo. String sem ? nunca é nulo.
  • valor! — "eu garanto que não é nulo aqui". Se for, o app quebra.
  • a ?? b — usa a; se for nulo, usa b. Ex.: user?.nome ?? 'Carregando...'.
  • a?.b — só acessa b se a não for nulo; senão o resultado é nulo.

C4Future, async/await e Stream

  • Future — um valor que chega depois (uma leitura do banco, por exemplo). await espera ele chegar sem travar a tela; só funciona dentro de função marcada com async.
  • Stream — uma sequência de valores ao longo do tempo. O Firestore usa isso para avisar sempre que um documento muda (.snapshots()).
  • stream.first — pega só o primeiro valor de um stream, como se fosse um Future. Aparece quando o código precisa ler uma vez só.
  • Future.wait([a, b]) — dispara várias leituras ao mesmo tempo e espera todas. Bem mais rápido que uma depois da outra.

C5Riverpod: os providers

Riverpod é a biblioteca que entrega dados e objetos para quem precisa, sem passar tudo de tela em tela. Um provider é uma variável global que sabe criar um valor:

C6ConsumerWidget, ref.watch e ref.read

Uma tela que usa providers estende ConsumerWidget (ou ConsumerStatefulWidget se tiver estado). Ela recebe um ref, que é a porta para os providers:

  • ref.watch(provider) — lê e fica observando. Quando o valor muda, a tela redesenha. Usado dentro do build.
  • ref.read(provider) — lê uma vez, sem observar. Usado dentro de ações (o onPressed de um botão).
  • ref.listen(provider, (antes, depois) {...}) — executa algo quando o valor muda, sem redesenhar.
final grupos = ref.watch(meusGruposProvider);          // tela observa
...
onPressed: () => ref.read(authControllerProvider.notifier).logout(),  // ação

.notifier devolve o controller em si (com os métodos), em vez do estado dele.

C7AsyncValue: carregando, erro ou dado

Quando a tela observa um StreamProvider ou FutureProvider, ela recebe um AsyncValue, que está sempre em um de três estados. O .when obriga a tratar os três:

return grupos.when(
  data: (lista) => ...,                                  // chegou
  loading: () => const CircularProgressIndicator(),      // carregando
  error: (e, _) => Text('Erro: $e'),                     // deu erro
);
  • maybeWhen(data: ..., orElse: ...) — trata só o que interessa; o resto cai no orElse.
  • valueOrNull — o dado, ou nulo se ainda não chegou. Usado quando não precisa mostrar carregamento.
  • .isLoading, .hasError, .error — perguntas diretas sobre o estado.

C8Controller com AsyncNotifier

Toda ação que grava algo passa por um controller. Todos seguem o mesmo molde:

class RachaController extends AsyncNotifier<void> {
  @override
  Future<void> build() async {}               // estado inicial: nada

  Future<void> remover(String rachaId) async {
    state = const AsyncLoading();              // 1. avisa "carregando"
    state = await AsyncValue.guard(() {        // 2. executa
      return ref.read(rachaRepositoryProvider).remover(rachaId);
    });                                        // 3. vira dado ou erro
  }
}

AsyncValue.guard executa a função e captura qualquer erro, guardando no state em vez de deixar o app quebrar. A tela observa esse state para mostrar o botão girando (isLoading) ou a mensagem de erro (error).

C9Navegação: go_router e Navigator

  • context.push('/rachas/abc') — abre a tela da rota, empilhando por cima da atual.
  • context.push('/grupos/x', extra: grupo) — extra passa um objeto inteiro para a próxima tela.
  • context.pop() ou Navigator.of(context).pop() — fecha a tela (ou diálogo) de cima.
  • Navigator.pop(context, valor) — fecha devolvendo um valor para quem abriu. É assim que os diálogos de confirmação devolvem true/false.

As rotas estão todas em 1.2 app_router.dart.

C10Firestore: o banco de dados

  • Coleção é uma pasta de documentos; cada documento é um mapa de campos ({'nome': 'Ana', 'idade': 20}). Ex.: users/{uid}.
  • Subcoleção é uma coleção dentro de um documento. Ex.: rachas/{id}/participantes — os participantes daquele racha.
  • .get() lê uma vez (Future). .snapshots() fica ouvindo (Stream).
  • .where('campo', isEqualTo: x) filtra.
  • collectionGroup('avaliacoes') busca em todas as subcoleções com esse nome, de todos os rachas de uma vez.
  • WriteBatch — junta várias gravações e manda tudo junto: ou grava tudo, ou nada. Usado sempre que uma falha no meio deixaria o banco inconsistente.

Quem decide quem pode ler e gravar cada coisa é o arquivo firestore.rules, fora da pasta lib/.

C11Recursos do Dart 3 que aparecem bastante

  • switch como expressão — devolve um valor direto: final cor = switch (status) { pendente => amarelo, recusado => vermelho, ... };
  • Records — vários valores juntos sem criar classe: final (rotulo, cor) = ('Confirmado', verde);
  • if/for dentro de listas — [ if (isAdmin) Botao(), for (final p in lista) Linha(p) ].
  • Spread ...lista — "espalha" os itens de uma lista dentro de outra.
  • extension — adiciona métodos a um tipo que já existe. Ex.: TipoCampo.society.label (ver 2.1 enums.dart).

C12mounted depois de await

Depois de um await, a pessoa pode ter saído da tela. Usar o context de uma tela que já fechou quebra o app. Por isso aparece muito:

await ref.read(authControllerProvider.notifier).login(...);
if (!mounted) return;            // a tela ainda existe? senão, para aqui
ScaffoldMessenger.of(context).showSnackBar(...);

Em funções soltas (fora de um State) a mesma checagem é context.mounted.

    Precisa vir antes de qualquer await no main: o Firebase usa código nativo do celular, e essa linha liga a ponte entre Flutter e o sistema antes do app desenhar.
  • Firebase.initializeApp
    Conecta ao projeto racha-app-ghad-108ab. As chaves vêm de firebase_options.dart.
  • initializeDateFormatting('pt_BR')
    Carrega os nomes de dias e meses em português. Sem isso, DateFormat("EEEE", 'pt_BR') mostraria "Saturday" ou daria erro.

    Envolve o app inteiro. É onde o Riverpod guarda os valores de todos os providers (C5). Sem ele, nenhum ref.watch funciona.
  • _aoReceberEmSegundoPlano
    Função vazia exigida pelo Firebase Messaging para notificações que chegam com o app fechado. Precisa ser função de nível de topo (fora de classe) e ter @pragma('vm:entry-point'), porque roda num processo separado.

1.2 app_router.dart

lib/core/router/app_router.dart

A lista de todas as telas do app e o endereço de cada uma, além da regra que manda quem não está logado para o login.

final routerProvider = Provider<GoRouter>((ref) {
  final authState = ref.watch(authStateChangesProvider);

  return GoRouter(
    initialLocation: '/login',
    refreshListenable: GoRouterRefreshStream(ref, authStateChangesProvider),
    redirect: (context, state) {
      final logado = authState.valueOrNull != null;
      final indoParaAuth =
          state.matchedLocation == '/login' || state.matchedLocation == '/cadastro';

      if (!logado && !indoParaAuth) return '/login';
      if (logado && indoParaAuth) return '/home';
      return null;
    },
    routes: [
      GoRoute(path: '/login', builder: (context, state) => const LoginScreen()),
      GoRoute(path: '/home', builder: (context, state) => const HomeScreen()),
      GoRoute(
        path: '/rachas/:id',
        builder: (context, state) =>
            RachaDetalheScreen(rachaId: state.pathParameters['id']!),
      ),
      GoRoute(
        path: '/grupos/:id',
        builder: (context, state) =>
            GrupoDetalheScreen(grupo: state.extra as GrupoModel),
      ),
      // ... mais 12 rotas no mesmo formato
    ],
  );
});
  • redirect
    Roda antes de toda navegação. Deslogado tentando abrir qualquer tela → vai para /login. Logado tentando abrir login ou cadastro → vai para /home. return null = "pode seguir". É por isso que nenhuma tela precisa navegar depois do login: quando o Firebase avisa que alguém entrou, o redirect manda para a Home sozinho.
  • refreshListenable
    Faz o redirect rodar de novo toda vez que o estado de login muda. GoRouterRefreshStream, no fim do arquivo, é uma pequena ponte: escuta o provider do Riverpod e avisa o go_router.
  • :id e pathParameters
    /rachas/:id aceita qualquer valor no lugar de :id. A tela recebe esse valor por state.pathParameters['id'].
  • extra
    Algumas rotas recebem o objeto inteiro em vez de só o id (state.extra as GrupoModel), para a tela já abrir com os dados sem precisar buscar de novo. Ver C9.

Parte 2 — Modelos

O que é um modelo

Um modelo é a "ficha" de uma coisa do app: um usuário, um racha, um participante. É uma classe só com dados, sem tela e sem banco. Ela sabe duas coisas: virar mapa para ser gravada no Firestore, e ser montada a partir de um mapa lido de lá.

2.2user_model.dart — o padrão de todo modelo

Este é o modelo explicado em detalhe. Todos os outros modelos seguem exatamente o mesmo formato, então nas próximas seções só aparece o que for diferente.

class UserModel {

  final String nome;

  • Tudo final
    Um modelo nunca muda depois de criado. Para "mudar", cria-se uma cópia com o valor novo (o copyWith, abaixo). Isso evita bugs de uma tela alterar o objeto que outra está mostrando.
  • String? fotoPerfilBase64
    Opcional: quem não tirou foto fica com nulo (C3). A foto é guardada como texto base64 dentro do documento (ver 3.2).
  • Não tem senha
    De propósito: a senha fica com o Firebase Authentication, que guarda com segurança. Guardar de novo aqui seria redundante e menos seguro.

    peso: (map['peso'] as num).toDouble(),
    createdAt: (map['createdAt'] as Timestamp).toDate(),
    fcmToken: map['fcmToken'] as String?,
  );
}
  • factory
    Um construtor que pode ter lógica antes de criar o objeto. Aqui ele lê o mapa que veio do Firestore e monta o UserModel.
  • Map<String, dynamic>
    Um documento do Firestore chega assim: chave em texto, valor de qualquer tipo. O as String diz qual tipo esperar.
  • (map['peso'] as num).toDouble()
    O Firestore devolve 70 como inteiro e 70.5 como decimal. num aceita os dois, e o toDouble() padroniza.
  • Timestamp → DateTime
    O Firestore guarda datas no tipo dele, Timestamp; .toDate() converte para o DateTime do Dart.
  • O id vem separado
    O id é o nome do documento, não um campo dentro dele. Por isso é passado à parte.

O que é um service

Um service é uma classe que conversa com algo de fora do app: o login do Firebase, o GPS, um site de busca de endereço, as notificações do celular. Cada uma "embrulha" uma biblioteca externa, para o resto do app não depender dela diretamente.

class LocationService {
  Future<PosicaoAtual> obterPosicaoAtual() async {
    if (!await Geolocator.isLocationServiceEnabled()) {
      throw Exception('Ative a localização (GPS) do aparelho e tente de novo.');
    }

    var permissao = await Geolocator.checkPermission();
    if (permissao == LocationPermission.denied) {
      permissao = await Geolocator.requestPermission();
    }
    if (permissao == LocationPermission.denied ||
        permissao == LocationPermission.deniedForever) {
      throw Exception('Permissão de localização negada.');
    }

    final posicao = await Geolocator.getCurrentPosition(
      locationSettings: const LocationSettings(accuracy: LocationAccuracy.high),
    );
    return PosicaoAtual(
      ponto: GeoPoint(posicao.latitude, posicao.longitude),
      precisaoMetros: posicao.accuracy,
    );
  }
}
  • A ordem das checagens
    GPS ligado? → tem permissão? se não, pede → negou? lança erro. Só então lê a posição. A tela que chama mostra a mensagem do Exception para a pessoa.
  • throw Exception(...)
    Interrompe a função e manda o erro para quem chamou, que trata com try/catch.
  • LocationAccuracy.high
    Liga o GPS de verdade. Mais lento, mas acerta a rua em vez da região.
  • PosicaoAtual
    Classe do mesmo arquivo que guarda o ponto e a precisão em metros. No computador o navegador estima a posição pelo Wi-Fi e erra por quilômetros; com a precisão, a tela consegue avisar isso (imprecisa = mais de 1 km).

Future<List<EnderecoEncontrado>> buscar(String termo) async {
  final limpo = termo.trim();
  if (limpo.length < 3) return const [];

  final digitos = limpo.replaceAll(RegExp(r'\D'), '');
  if (digitos.length == 8 && RegExp(r'^[\d\s-]+$').hasMatch(limpo)) {
    final endereco = await _enderecoDoCep(digitos);
    if (endereco != null) {
      final achados = await _coordenadasDe(endereco);
      if (achados.isNotEmpty) return achados;
    }
  }
  return _coordenadasDe(limpo);
}
  • Como sabe que é CEP
    RegExp(r'\D') casa tudo que não é dígito; trocando por vazio, sobram só os números. Oito dígitos (com ou sem hífen) = CEP.
  • Por que dois serviços
    O ViaCEP devolve rua e bairro, mas não coordenadas. O Nominatim devolve coordenadas a partir do texto.
  • jsonDecode
    Nos métodos privados, a resposta vem em JSON (texto) e jsonDecode transforma em mapas e listas do Dart.
  • countrycodes: 'br'
    Limita a busca ao Brasil — sem isso, "Rua das Flores" trazia Portugal primeiro.
  • Busca só ao confirmar
    O Nominatim pede no máximo uma consulta por segundo, então a tela só busca quando a pessoa aperta enter, nunca a cada letra.

Parte 4 — Repositories

O que é um repository

Um repository é a única porta para uma coleção do banco. Toda leitura e gravação de usuários passa pelo UserRepository; de rachas, pelo RachaRepository, e assim por diante. A tela nunca escreve FirebaseFirestore — ela pede ao controller, que pede ao repository.

4.1user_repository.dart — o padrão de todo repository

lib/repositories/user_repository.dart
class UserRepository {
  UserRepository(this._firestore);

  final FirebaseFirestore _firestore;

  CollectionReference<Map<String, dynamic>> get _collection =>
      _firestore.collection(FirestorePaths.users);

  Future<void> criar(UserModel user) {
    return _collection.doc(user.id).set(user.toMap());
  }

  Future<UserModel?> buscarPorId(String id) async {
    final doc = await _collection.doc(id).get();
    if (!doc.exists) return null;
    return UserModel.fromMap(doc.id, doc.data()!);
  }

  Stream<UserModel?> observar(String id) {
    return _collection.doc(id).snapshots().map((doc) {
      if (!doc.exists) return null;
      return UserModel.fromMap(doc.id, doc.data()!);
    });
  }

  Future<void> atualizar(UserModel user) {
    return _collection.doc(user.id).update(user.toMap());
  }
}
  • _collection
    Atalho para a coleção users. O nome vem de FirestorePaths (6.6), para não espalhar textos soltos pelo código.
  • set x update
    set grava o documento inteiro (cria se não existe). update muda só os campos passados e falha se o documento não existir.
  • doc(user.id)
    O documento do usuário tem como nome o mesmo id do login (uid). Assim, achar o perfil de quem está logado é direto.
  • get() x snapshots()
    buscarPorId lê uma vez; observar fica ouvindo e entrega um UserModel novo a cada mudança (C10). O .map converte cada documento em modelo com o fromMap.

Future<void> finalizar(RachaModel racha) async {
  state = const AsyncLoading();
  state = await AsyncValue.guard(() async {
    final estatisticas = await ref.read(estatisticaRepositoryProvider)
        .observarPorRacha(racha.id).first;
    final pendentes = estatisticas.where((e) => !e.confirmada).length;
    if (pendentes > 0) {
      throw Exception('$pendentes estatística(s) ainda esperando conferência...');
    }

    final batch = ref.read(firestoreProvider).batch();
    rachaRepo.atualizarStatusEmLote(batch, rachaId: racha.id, status: RachaStatus.finalizado);

    final grupoId = racha.grupoId;
    if (grupoId != null) {
      final grupo = await ref.read(grupoRepositoryProvider).buscarPorId(grupoId);
      if (grupo != null) {
        final proximaRef = rachaRepo.novoDocRef();
        final proxima = RachaModel(
          id: proximaRef.id,
          grupoId: grupo.id,
          dataHora: proximaOcorrencia(grupo.diaSemana, grupo.horario),
          anotadores: grupo.auxiliares,
          ...
        );
        rachaRepo.criarEmLote(batch, proximaRef, proxima);
        for (final userId in {grupo.adminId, ...grupo.membrosFixos}) {
          participanteRepo.convidarEmLote(batch, rachaId: proximaRef.id, userId: userId);
        }
      }
    }
    await batch.commit();
  });
}
  • Primeiro: estatísticas conferidas
    Não finaliza se alguma estatística ainda espera conferência — depois de finalizada ela ficaria de fora do ranking sem ninguém perceber.
  • Racha de grupo gera o próximo
    Lê a configuração do grupo, calcula a próxima data (proximaOcorrencia, 6.6), cria a rodada e convida o admin e todos os membros fixos.
  • {grupo.adminId, ...grupo.membrosFixos}
    Chaves criam um Set, que não aceita repetidos: se o admin também estiver na lista de membros, ele não é convidado duas vezes.
  • Tudo num batch
    Encerrar uma e criar a outra acontecem juntos. Se caísse no meio, o grupo poderia ficar sem nenhuma rodada aberta.

distribuirPorSetor — a regra da posição secundária

Coloca cada jogador no setor da posição principal. Depois, onde faltar gente (comparando com o alvo):

  1. Primeiro entram os que não escolheram posição — não tiram ninguém do lugar.
  2. Se ainda faltar, puxa de um setor que está sobrando alguém cuja posição secundária é o setor em falta. Entre os candidatos, sai o de menor nota: os melhores continuam onde jogam melhor.
  3. Se ninguém tem esse setor como secundária, o time joga desfalcado ali. Forçar alguém a jogar fora das duas posições dele seria pior.

Exemplo: confirmaram dez atacantes e nenhum meia. Os atacantes que marcaram "também jogo de meia" descem para o meio. Os que só jogam na frente ficam lá.

  if (noSetorA != noSetorB) return noSetorA < noSetorB ? timeA : timeB;
  if (timeA.length != timeB.length) return timeA.length < timeB.length ? timeA : timeB;
  return _somaNota(timeA) <= _somaNota(timeB) ? timeA : timeB;
}

Vai para o time com menos gente naquele setor; empatou, o com menos gente no total; empatou de novo, o com menos nota somada. Isso já espalha os melhores: o melhor vai para A, o segundo para B, o terceiro para o time mais fraco…

Passo 3: o ajuste fino com quatro critérios

Depois da distribuição, o algoritmo testa todas as trocas possíveis entre um jogador do time A e um do time B do mesmo setor, e faz a que mais aproxima os times. Repete até nenhuma troca melhorar.

double _desequilibrio(_Somas a, int tamA, _Somas b, int tamB) {
  double dif(double somaA, double somaB, double escala) =>
      (somaA / tamA - somaB / tamB).abs() / escala;

  return pesoNota * dif(a.nota, b.nota, escalaNota) +
      pesoGols * dif(a.gols, b.gols, escalaGols) +
      pesoIdade * dif(a.idade, b.idade, escalaIdade) +
      pesoCorporal * dif(a.peso, b.peso, escalaPeso);
}
  • Um número só
    O desequilíbrio é a soma das diferenças das médias de cada critério, cada uma dividida pela escala e multiplicada pelo peso. Zero = perfeitamente equilibrado.
  • Média, não soma
    Os times podem ter um jogador de diferença. Somas iguais, nesse caso, significariam o time menor mais forte por jogador.
  • Só troca dentro do mesmo setor
    Goleiro por goleiro, meia por meia. Por isso o passo 3 nunca desfaz os passos 1 e 2.
  • .abs()
    Valor absoluto: tanto faz qual time é mais forte, só importa o tamanho da diferença.
Map<String, double> _golsEfetivos(List<JogadorElegivel> todos) {
  final conhecidos = [for (final j in todos) if (j.golsPorJogo != null) j.golsPorJogo!];
  final media = conhecidos.isEmpty ? 0.0 : conhecidos.reduce((a, b) => a + b) / conhecidos.length;
  return {for (final j in todos) j.id: j.golsPorJogo ?? media};
}

Quem não tem histórico de gols entra com a média do grupo, não com zero. Com zero, o algoritmo juntaria todos os novatos de um lado para "compensar" o artilheiro do outro.

Exemplo para explicar na hora: dois times com a mesma nota média, mas um tem os quatro jogadores de 18 anos e o outro os de 40. O desequilíbrio de idade é alto. O algoritmo procura dois jogadores do mesmo setor, um novo no A e um velho no B, e troca. A nota continua igual, e a idade média se aproxima.

_Somas, no fim do arquivo, guarda as somas de cada critério de um time. Assim, testar uma troca é só "tira a contribuição de um e põe a do outro", sem recalcular o time inteiro — importante porque num campão são centenas de trocas testadas por rodada.

Como se sabe que funciona: os testes em test/core/balanceamento/ montam casos (todos os novos de um lado, os artilheiros juntos) e conferem o resultado. Zerando o peso da idade ou dos gols, exatamente o teste correspondente falha.

Perguntas que o professor pode fazer

Respostas curtas, com o link para a explicação completa.

Onde o app usa a câmera?
No FotoPerfilPicker, com ImagePicker().pickImage(source: ImageSource.camera), no cadastro e na edição de perfil. → 7.3
Como a tela sabe que alguém fez login e vai para a Home?
O router observa o stream de login do Firebase. Quando muda, o redirect roda de novo e manda para /home. A tela de login não navega. → 1.2
Qual a diferença entre ref.watch e ref.read?
watch lê e fica observando, redesenhando a tela quando muda (usado no build). read lê uma vez (usado em botões). → C6
Para que serve o dispose?
Libera os TextEditingControllers quando a tela fecha, para não ficar ocupando memória. → 8.1
O que é fromMap e toMap?
Conversões entre o objeto do Dart e o mapa que o Firestore grava. toMap para salvar, fromMap para ler. → 2.2
Por que separar em services, repositories e controllers?
Cada camada tem uma responsabilidade. Só services e repositories conhecem o Firebase; a lógica de times e ranking fica em core/ sem Firebase, e por isso dá para testá-la sem internet. → 0.2
Como os times são balanceados?
Um goleiro por time; mesma quantidade em defesa, meio e ataque, pela posição principal; depois troca jogadores do mesmo setor até os times ficarem parecidos em nota (peso 1,0), gols (0,6), idade (0,4) e peso corporal (0,15). → 6.3
E se faltar meia e sobrar atacante?
Primeiro entra quem não escolheu posição. Depois, atacantes que marcaram meia como posição secundária descem, começando pelos de menor nota. Ninguém joga fora das duas posições que escolheu. → 6.2
Que nota tem um jogador novo ou convidado?
3,0, o meio da escala, para não puxar o equilíbrio para nenhum lado. Nos gols, a média do grupo. → 6.1
Como é calculado o ranking?
Sempre do zero, a partir de todas as avaliações, estatísticas conferidas e MVPs do jogador, numa função só (agregarRanking), usada pelo ranking geral e pelo do grupo. Ordem: mais MVPs, depois maior média. → 6.4
Como é escolhido o MVP?
Maior média de notas na rodada; empate, quem recebeu mais avaliações. Convidado nunca é MVP. → 6.5
Um jogador pode inventar os próprios gols?
Pode lançar, mas fica "aguardando conferência" e não conta no ranking até o admin ou um anotador confirmar. O anotador não confere os próprios números, e o racha só finaliza com tudo conferido. A regra também está no firestore.rules. → 5.11
O que acontece quando o admin finaliza uma rodada de grupo?
Num único batch: a rodada vira "finalizada", nasce a próxima (data calculada pelo dia da semana) e o admin e os membros fixos são convidados. → 5.5
O que é um WriteBatch e por que usar?
Várias gravações enviadas juntas: ou todas acontecem, ou nenhuma. Evita estados quebrados, como um racha sem participantes ou times atribuídos pela metade. → C10
Como funciona a busca por "Rachas Próximos"?
Pega a posição pelo GPS, baixa os grupos abertos e calcula a distância de cada um com a fórmula de haversine, filtrando pelo raio escolhido. → 8.9
Por que a foto é guardada em base64?
O Firebase Storage exige plano pago. A foto é comprimida, convertida em texto e gravada no documento. O StorageService isola isso para trocar depois sem mexer em quem chama. → 3.2
O que é o AsyncValue.guard?
Executa a ação e captura qualquer erro, guardando no estado do controller em vez de deixar o app quebrar. A tela lê isLoading e error desse estado. → C8
Por que tem "if (!mounted) return" depois de await?
Durante a espera a pessoa pode ter saído da tela; usar o context de uma tela fechada quebra o app. → C12
